# Memory Review Console — 架构与流程

> 一个宿主在 DeepSeek Harness（Cordis 插件体系）里的**长期记忆与人格审阅台**。
> 本文只讲机制，不含任何具体部署数据。

---

## 0. 这份文档写给谁

给三类人：

- **想装它的人** — 看第 1、2 节和 Part II 的流程就能判断它合不合用
- **想改它的人** — 看 Part I 的结构、写入口和扩展点
- **想抄它的设计的人** — 看 Part III，那里是我踩过的坑

一条前提：这套东西解决的不是「让模型记住更多」，而是**「让人能管住模型记住了什么」**。如果你只是想加个记忆库，不需要这么复杂。

# Part I 架构

## 1. 为什么是插件，不是独立程序

同一套界面有三种做法，我们试过前两种：

| 做法 | 问题 |
|---|---|
| 独立 EXE / Electron | 主题、字体缩放、快捷键、深色模式全要自己实现一遍；高分屏上文字发虚、布局重叠，得手写 DPI 缩放 |
| iframe / 独立窗口 | 宿主主题拿不到，切 tab 会丢状态，跨窗口通信要自己搭桥 |
| **插件（渲染进宿主槽位）** | 主题、深色、语言、快捷键自动跟随宿主；页面就是一组 React 组件 |

代价也很明确：**它只能在 Harness 里跑**，离开宿主就没有界面。这个代价我们接受了——因为它天生是"跟模型一起用"的东西。

## 2. 三个半边

```
┌─────────────────────────────────────────────────────────────┐
│  Host（Node，插件主进程）                                    │
│  · 注册 HTTP 路由  /<plugin-id>/api                          │
│  · 读文件（只读白名单）                                       │
│  · 注册动态 systemPrompt section                             │
│  · 把写操作转成 CLI 子进程调用                                │
└───────────────┬─────────────────────────────────────────────┘
                │  HTTP (localhost, JSON)
┌───────────────▼─────────────────────────────────────────────┐
│  Client（浏览器里的 React 组件）                              │
│  · 渲染进宿主槽位：主区 + 侧栏面板列表                        │
│  · 只做展示与交互；不做计算、不写文件                          │
└───────────────┬─────────────────────────────────────────────┘
                │  spawn
┌───────────────▼─────────────────────────────────────────────┐
│  CLI（纯 Node / Python 脚本）                                │
│  · pending.mjs   候选队列状态机（收 / 扔 / 改投）             │
│  · memctl.mjs    记忆增删改、衰减、注入、权重                 │
│  · mem-index.py  FTS5 索引：build / recall / stats           │
└─────────────────────────────────────────────────────────────┘
```

**为什么把逻辑全塞进 CLI**：这几个脚本在没有界面的时候也是完整可用的（定时任务、其他会话、命令行都能调）。界面只是它们的一个前端。反过来，如果逻辑写在 host 里，脱离界面就没法用，而且两份实现迟早会分叉。

**host 不直接写文件**（唯一的例外见 5.3）。所有写操作都是 `spawn(node|python, [script, ...args])`，拿退出码和 stdout 决定成败。

## 3. 分层模型

记忆不是一坨，是六层，区别在于**什么时候能到模型面前**：

| 层 | 载体 | 到达方式 | 成本 |
|---|---|---|---|
| **身份** | `persona.md` → 宿主配置里的 `personaPrefix` | 每轮（系统提示） | 每轮付费 |
| **纪律** | `rules.md` → 动态 systemPrompt section | 每轮（系统提示） | 每轮付费 |
| **长期** | `facts.md` / `self.md` / `voices.md` | 模型主动读，或被检索命中 | 读到才算 |
| **候选** | `pending-facts.jsonl` | 人审时看 | 0 |
| **衰减** | `decay.jsonl` | 流程触发时按预算注入一段 | 注入时 |
| **归档** | `full.jsonl` / 日记 / 每日流水 | 检索命中才读 | 0 |

**这张表是整套设计的地基**，它要回答的问题只有一个：*什么东西能在模型开口之前就到场？* 只有前两行。

所有「写进文件模型就知道了」的想法都是错的。写进第三层及以下的文件，模型只有在主动读、被检索命中、或被注入时才知道。

### 3.1 为什么身份和纪律要分开

同一个系统提示里的两段，本来可以写在一起。分开是因为**它们的变更节奏和风险等级不同**：

| | 身份（persona） | 纪律（rules） |
|---|---|---|
| 内容 | 我是谁、什么语气、什么画面感 | 什么必须先问、什么绝不做、输出什么格式 |
| 变更频率 | 几个月一次 | 随工作演进反复增删 |
| 写坏的后果 | **换人** | 做错事 |
| 注入通道 | 编译进配置（有校验闸 + 快照） | 运行时读盘（改完保存即生效） |
| 判据 | 「我是谁」→ 这里 | 「我怎么做」→ 那里 |

**同一个技术不要用在两个风险等级上。** 所以我们没有把 persona 也改成读盘——它保留"编译 + 快照 + 结构校验"那道慢仪式，那道闸就是它的保护。

## 4. 单一写入口

四条写路径，各自只有一个入口：

| 想改什么 | 唯一入口 | 界面能不能直接写 |
|---|---|---|
| 候选记忆的状态 | `pending.mjs accept / reject` | ❌ 只能调 CLI |
| 记忆条目 / 权重 / 衰减 | `memctl.mjs` | ❌ 只能调 CLI |
| 纪律 | `rules.md` 本体 | ✅ **可以**（见 5.3） |
| 身份 | `persona.md` + 同步脚本 | ❌ 只能改源，重建走脚本 |

判断一条路径给不给界面写，用的不是"它是文件还是数据库"，而是：

> **它是「数据」还是「配置」？**
> 数据 = 有状态机、有第二个写入者、写坏会毁东西 → 只走 CLI。
> 配置 = 一段人写的文本、没有并发、写坏能一眼看出 → 允许界面直写，但要带护栏。

## 5. 注入通道

### 5.1 机制

宿主的 systemPrompt 服务允许一段 section 的正文是**函数**：

```ts
interface PromptSection {
  name: string
  order: number
  text: string | ((ctx: AssembleContext) => string)   // ← 每次组装时现算
}
```

所以可以这样注册：

```js
ctx.effect(() => ctx.systemPrompt.section({
  name: 'plugin-rules',
  order: 900,
  text: () => readRulesFromDisk(),   // 每次组装系统提示时读一次盘
}), 'rules section')
```

### 5.2 这样做的收益

改一条纪律 = **改一个 markdown 文件，保存，下一条消息生效**。
不用同步脚本、不用碰 YAML、不用重启。

对照另一种写法（把纪律写进宿主的配置 YAML）：
改一条 → 改 md → 跑比对脚本 → 手动把段落贴进 YAML → 触发重载。
中间那一步能把会话写坏。

### 5.3 护栏（必须做，否则是负优化）

读盘注入有一个新的失败模式：**文件被清空或读不到时，模型会静默地失去约束**。原来的编译式写法会当场报错，读盘式不会。

所以至少要有：

1. **读不到 → 返回空串并记一条警告**，不静默装死
2. **长度异常 → 报警**（比如从 300 字掉到 20 字，或超过阈值）
3. **界面能显示「文件里多少字 / 系统提示实际注入多少字」** —— 这两个数字不一致就说明链路断了

第 3 条最关键：它把"改了半天没生效"从猜测变成一眼可见。

### 5.4 写盘的三道保险

纪律文件允许界面写，所以写的时候：

| 保险 | 做法 |
|---|---|
| 别覆盖别人的编辑 | 保存时带上读到文件时的 `mtime`，对不上就**拒绝**并要求重新加载 |
| 写坏能退 | 每次写前复制一份 `.bak-<时间戳>` |
| 写一半不会烂 | 写临时文件 + `rename` 原子替换 |

## 6. 索引与检索

### 6.1 是什么

SQLite + FTS5（BM25）+ 中文分词。把文档、日记、对话流水、衰减层、长期记忆切成块，一个库里查。

```
python mem-index.py build      # 建 / 增量
python mem-index.py recall "问题" --k 5
```

分块规则按层不同：文档按 `##` 小节、日记按日期、会话按回合。

### 6.2 为什么要层权重

纯 BM25 有个偏向：**体量大的层会压制体量小的层**。日记几百块、规范文件十来块，同样命中时日记的分数天然更高，于是"他的原话"总排在第 2–3 位。

加一层系数就能纠正：

```sql
ORDER BY bm25(...) * CASE layer
  WHEN 'voices' THEN 1.3 WHEN 'self' THEN 1.3 WHEN 'rules' THEN 1.3
  WHEN 'diary' THEN 0.95 WHEN 'session' THEN 0.95
  ELSE 1.0 END
```

（BM25 返回负数，越负越相关，所以 ×1.3 是提权、×0.95 是压后。）

实测效果：查"某人说过某句话"，原话层从第 3 升到第 1；查"我犯过的错"，失败模式层稳定第 1。

### 6.3 输出要自洽

排序按加权分，但显示的分数如果还是原始分，列表看起来就是乱的（-22 排在 -27 前面）。所以两个都给：`score`（加权，跟排序一致）+ `score_raw`（原始，判断"到底像不像"）。

## 7. 衰减与生命周期

### 7.1 参数

| 权重 | 每天衰减 | 清晰度下限 | 多久没读就出局 |
|---|---|---|---|
| 4–5 | 0.02 | 0.40 | 永不 |
| 3 | 0.05 | 0.15 | 90 天 |
| ≤2 | 0.10 | 0 | 30 天 |

被读到（注入 / 检索命中）→ 清晰度 +0.15，`lastUsed` 刷新。

### 7.2 一个真实的设计 bug（值得单独讲）

出局条件是「清晰度 ≤ 0.1 且超过年龄门槛」。但权重 3 的**下限是 0.15**——永远掉不到 0.1。

结果：**权重 3 的"90 天出局"是死代码**，从上线起就没生效过。表现是用户报"这一档怎么也不出局"。

修法不是把下限调低，而是让出局门槛跟下限对齐：

```js
const gate = Math.max(0.1, floorOf(imp))
if (clarity <= gate && ageDays >= exitAge) → 出局
```

教训：**两个阈值分别写在两处，就看不出它们互相矛盾**。凡是"A 不满足 B 的条件"，都要在同一个函数里能一眼看到。

### 7.3 注入排序：新近性 + 配额

按预算（默认 800 字）从衰减层取若干条拼成一段文本。原来的排序是 `权重 × 清晰度`，问题：

- 同分条目多时，永远取最**早**的那几条 → 昨天写的进不去
- 这一层的定位明明是"最近该记得的事"

改成：

```
score = imp × clarity × (1 + 0.6 · e^(−age/14))     // age 用创建时间，半衰 14 天
```

再加每档配额（5:50% / 4:35% / 3:15%，≤2 不占名额），分两遍填充（第一遍守配额，第二遍预算有剩就放宽）。

**为什么 age 必须用"创建时间"而不是"上次读到时间"**：后者会被注入本身刷新，于是"被注入 → 变新鲜 → 又被注入"，形成自我强化闭环——换了个理由锁死同一批条目。

## 8. 安全模型

| 面 | 做法 |
|---|---|
| 监听地址 | 只绑 `127.0.0.1` |
| 鉴权 | **无**。本机进程本来就能直接读文件，加鉴权只是仪式 |
| 跨站 | 响应不加 CORS 头，别的网站读不到 |
| 读文件 | 键名白名单 + 文件名正则（挡 `../`） |
| 写文件 | 默认不走 HTTP；唯一可写的配置走 mtime + 备份 + 原子替换 |
| 子进程 | 只跑仓库内固定脚本，参数来自白名单字段，不拼 shell |

**不做的**：不做 token 鉴权、不做用户系统、不做远程访问。这是本地工具，假装成服务反而增加攻击面。

## 9. 已知限制

诚实列出来，省得别人踩：

1. **host 改动要重启整个宿主**（模块级缓存）；client 改动刷新页面即可。CLI 每次调用重新读。
2. 面板高度依赖宿主容器，滚动区域自己管。
3. 自检页（跨文件重复检测）的状态在切 tab 时重置。
4. 没有快照回滚——回滚意味着写身份文件，风险大于收益，故意不做。
5. 没有索引重建按钮，重建走命令行。
6. 界面文案目前只有中文（locale 文件在，但 UI 字符串是硬编码）。

# Part II 流程

## A. 一条候选记忆的一生

```
① 产生
   模型判断「这条以后用得上，但不确定该放哪层」→ pending.mjs add
   也可能是人手动加

② 排队
   pending-facts.jsonl：{ id, text, type, imp, src, status: pending }

③ 审
   界面「待审」页：卡片 → 四个去处
     ├ 收进衰减层     accept
     ├ 收进长期       accept --to facts|self|voices --section <节名>
     ├ 扔掉           reject --reason <理由>
     └ 改措辞         --wording <新文本>

④ 落
   · 收进长期 → 写进目标文件的指定小节 + 归档进衰减层（同时记 to/section）
   · 状态改成 accepted/rejected，**不删除**，留档可查

⑤ 之后
   衰减层按 7.1 的节奏掉清晰度；被注入或检索命中则续命；
   掉到门槛且够年龄 → 移出衰减层（全量档里仍在）
```

关键设计：**队列只追加不删除**。收和扔都留记录，因为"当时为什么扔掉"本身是有价值的判断素材。

## B. 改一条纪律（快通道）

```
1. 打开「规则」页
2. 编辑 → 保存
3. 页面带 mtime + 新正文 → host
4. host：mtime 对得上？→ 备份 → 写临时文件 → rename
5. 页面自动重新组装一次系统提示，显示「实际注入 N 字」
6. 下一条消息就按新纪律走
```

失败分支：

| 情况 | 表现 |
|---|---|
| 文件在别处被改过 | 拒绝保存，提示重新加载（草稿保留在编辑框里）|
| 写盘失败 | 页面报错，原文件未被改动 |
| 读不到文件 | 注入空串 + 警告，页面亮红 |

## C. 改人格（慢通道）

```
1. 存快照（内容没变会复用现有快照）
2. 改 persona.md
3. 跑同步脚本 → 输出 diff 和「可粘贴段」（脚本只读，不写配置）
4. 人把段落贴进宿主配置的 personaPrefix
5. 宿主热重载系统提示
6. 验证：再跑一次同步脚本，应该显示「一致」
```

**为什么第 4 步要人来做**：写坏 YAML 会当场把会话弄坏，而这一步恰好最容易被脚本"智能处理"掉。慢一点，但坏了能立刻看出来。

## D. 检索

```
输入框 → recall "问题" --k N
      → host：spawn python mem-index.py recall
      → 返回 [{ layer, head, score, score_raw, snippet, path }]
      → 卡片列表：层标签 + 标题 + 分数 + 摘要 + 源文件路径
```

python 解释器的位置**不硬编码**：问仓库里的运行时探测脚本要（它是"这台机器上 node/python 在哪"的唯一真相），问一次缓存。

## E. 调权重（含审计）

```
界面下拉 / memctl imp <id> --imp N [--why "..."]
  → 校验 1–5
  → 找到条目，记录旧值
  → 写回 decay.jsonl
  → 追加一行到 imp-log.jsonl：{ at, id, from, to, why, text }
  → 打印两个后果：寿命变化、注入权重变化
```

**为什么只允许改权重，不允许改清晰度 / 删条目 / 改正文**：

| 想改 | 允许吗 | 理由 |
|---|---|---|
| 权重 | ✅ | 它是"意图"，人有权纠正模型的估计 |
| 清晰度 | ❌ | 它是"系统状态"（被读到就升），手改会破坏语义 |
| 删条目 | ❌ | 会破坏双层结构；要它消失就降权等它自然出局 |
| 正文 | ❌ | 改正文是"写记忆"，应该新增一条更正，保留演进痕迹 |

## F. 启动与故障

| 症状 | 原因 | 处理 |
|---|---|---|
| 页面 404 / 接口全挂 | host 改动后没重启 | 重启宿主 |
| 页面正常但按钮无反应 | 点击后调了错的 CLI（参数被另一个脚本当成"用法错误"吃掉了）| 看接口返回的原始输出，别只看 ok |
| 「规则」页注入数是 0 | section 注册失败或文件为空 | 看页面上那行错误 |
| 检索一直转 | python 路径没探到 | 跑运行时探测脚本确认 |
| 改了配置没生效 | 改了宿主配置但没热重载 | 看宿主日志 |

# Part III 踩过的坑（设计反模式）

这一节比前面都值钱，都是真踩过的。

### 1. 同一个数字存在两处，必有一处是旧的

文档写「纪律 78 字」，代码里是 381。这种事一天之内发生了三次。

**对策**：能在运行时算出来的数字，就不要在文档/常量里硬编码。界面上显示的计数一律实时读，文档里的数字一律标注日期。

### 2. "看起来像"不等于"是"

用前缀匹配判断"这几条记录是不是在说同一件事"，结果误判——它们只是碰巧共享一个开头 `【覆盖旧条】`。

**对策**：结构相似性只能用来**排序候选**，不能用来**下结论**。下结论之前必须读全文。

### 3. 用一个会被自己修改的字段做时间基准

用 `lastUsed`（上次被读的时间）算"新鲜度"，而注入本身就会刷新它 → 自我强化闭环。

**对策**：排序用的时间基准必须**只由外部事件改变**（创建时间、人手动操作），不能由系统自身的输出改变。

### 4. 设置页 = 第二份真相

把代码里的常量搬到配置文件里让人改，看着方便，实际导致"代码说 A、配置说 B"。

**对策**：常量留在代码里（有版本控制、能 diff、能回滚）。界面提供**只读的参数说明**，改还是改代码。

### 5. `ok: true` 可能什么都没做

把参数喂给了错误的 CLI，那个脚本打印了一句"用法"并退出 0。接口返回成功，界面显示"没反应"。

**对策**：判断成败不能只看退出码，要校验**输出是否符合预期格式**（比如 JSON 解析得出来）。

### 6. 阈值/下限分写在两处，矛盾看不出来

出局门槛 0.1 和清晰度下限 0.15 分别定义在不同函数里，于是 `≤ 0.1` 永远不可能成立。没有报错，只是静默失效。

**对策**：凡是"A 要满足 B 的条件"，让它们在同一个函数里相邻出现。

### 7. append-only 的清理要克制

发现重复条目就删，会破坏"保留演进痕迹"的设计；但留着又占注入名额。

**对策**：用降权 + 自然出局代替删除。全量档里永远留有原文，衰减层只决定"还要不要主动提起它"。
